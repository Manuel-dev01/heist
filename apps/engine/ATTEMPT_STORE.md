# Injected attempt store

The adapter in `src/attempt-store.ts` stores current, redacted harness attempt records in the existing `sql/001_attempts.sql` table. It accepts an explicitly injected driver with this minimal interface:

```ts
interface AttemptStoreDriver {
  query(sql: string, parameters: unknown[]): Promise<{ rows: readonly unknown[] }>;
}
```

It creates no connection, reads no environment or credentials, selects no default client, and imports no PostgreSQL dependency. The caller owns the connection, authentication, destination, query deadlines, transaction isolation, logging and shutdown. It is exported through the engine index; CLI and web persistence remain unwired.

## API

```ts
const store = createAttemptStore(alreadyConfiguredDriver);

const result = await store.append({ record, metadata: {
  executionEnvironment: 'local_simulation',
  sourceKind: 'fixture',
  cohortKind: 'readiness',
  corpusId: 'owned-suite:v1',
  replicateIndex: 0,
} });
// result.status: 'inserted' | 'replayed'
// result.attempt: { record, metadata, occurredAt, ingestedAt }

const byId = await store.getById(record.id);
const byHash = await store.getByHash(record.attemptHash);
// Both reads return one validated StoredAttempt, or null when absent.
```

Every append validates the complete harness `AttemptRecordSchema`, including canonical record hash, integer money strings, conservation and oracle relationships, then snapshots the record before asynchronous driver access. SQL-specific task identifiers, the 160 unsafe-call ceiling and supported timestamp precision are checked as well. This does not establish the origin or truth of supplied evidence.

Not every generic harness-schema-valid record is guaranteed storable. The harness has a two-MiB serialized-record limit; PostgreSQL separately enforces the schema's four-MiB JSONB-text representation limit and its UTF-8/JSONB rules. Decoded U+0000 and unpaired Unicode surrogates can be rejected by PostgreSQL even when a JavaScript JSON representation passes the generic harness validator. Such driver/constraint failures become value-free `DRIVER_FAILURE`; the adapter does not remove characters or alter the record/hash to make an insertion succeed.

The metadata object is strict and maps only to existing immutable ingestion columns:

| API field | SQL column | Allowed values |
|---|---|---|
| executionEnvironment | execution_environment | local_simulation, isolated_audit_replica |
| sourceKind | source_kind | fixture, serv, dolphin |
| cohortKind | cohort_kind | readiness, funds, secret_extraction, benign_utility, utility_under_attack |
| corpusId | corpus_id | Existing schema identifier grammar, 1–120 characters |
| replicateIndex | replicate_index | Integer 0–1,000,000 |

`record_json` receives the validated JSON snapshot and `occurred_at` receives its original `ts`. Generated projections remain generated by PostgreSQL. `ingested_at` is omitted from INSERT, so its existing database default sets it. Labels are caller assertions outside the record hash; they are not billing verification or authenticated provenance.

## Append-only and replay behavior

Append uses a fixed, parameterized `INSERT ... ON CONFLICT DO NOTHING RETURNING`. An identical replay compares the complete canonical stored record and all five metadata fields, then returns `replayed` with the original stored ingestion timestamp. Matching JSON with a different object-key order is identical. Changing content or ingestion metadata under the same identity raises `CONFLICT`; nothing is overwritten.

A conflict lookup selects by the valid ID or hash with `LIMIT 2`. Ordinary reads accept only a valid UUID or lowercase SHA-256 hash and use fixed `LIMIT 1` queries. There are no arbitrary table/query names, list methods, UPDATE, DELETE, TRUNCATE, upsert updates, automatic retries or transaction commands. Caller-owned READ COMMITTED operation supports the separate post-conflict read; stronger retained transaction snapshots can instead fail closed if a conflicting row is not visible.

All returned rows are checked again: strict JSONB row shape, complete record/hash validation, permitted metadata, and timestamp consistency. The driver must return parsed JSONB objects, plus ordinary valid JavaScript Date values or UTC ISO strings for timestamps. Lookup rows must match the requested identity/hash. Corrupt INSERT-returned rows are rejected as well.

Returned `occurredAt` and `ingestedAt` normalize driver timestamps to millisecond UTC ISO strings. Ordinary node-postgres Date results already have millisecond precision; finer database timestamp precision cannot be verified through such a driver. The exact original hashed `record.ts` remains unchanged, including up to six fractional digits. Records with more than six fractional digits are rejected before any append query and rejected as unsupported on read. PostgreSQL rounds finer input to microseconds, while JavaScript Date parsing truncates to milliseconds; rejecting that input avoids a valid commit followed by a timestamp-binding failure. No timestamp text or record hash is silently rewritten, and no client clock replaces the database ingestion timestamp on replay.

## Errors

`AttemptStoreError` exposes only a stable code and fixed, value-free message:

| Code | Meaning |
|---|---|
| INVALID_INPUT | Invalid driver, append input, record, metadata or lookup identity |
| CONFLICT | Existing immutable identity/content or metadata conflict |
| CORRUPT_ROW | Stored/returned evidence fails validation or consistency |
| DRIVER_FAILURE | Driver failure, malformed/excessive result, or missing post-conflict row |

No raw driver error, cause, query parameter, submitted record or connection detail is attached. An error after an INSERT is not proof that no row was committed; callers may resolve ambiguity through a validated lookup or a later identical replay.

## Validation status

The new suite has **71 offline driver-contract tests** and passes the engine's strict no-emit typecheck. Tests exercise invalid/tampered records, SQL-shaped bound data, exact forty-digit balances, replay/conflicts, both Date/ISO driver timestamps, corrupt rows, invalid result bounds and sanitized failures. A network-denying stub verifies that these tests make no fetch calls.

These tests use an injected query double. They do not parse SQL, open a database, prove transaction/concurrency behavior, or constitute a new PostgreSQL integration run. The existing **81 disposable PostgreSQL 16.14 schema checks** are separate evidence documented in `sql/README.md`. No live database, provider inference, wallet, network or credential access was used for this adapter work, and engine built output was left untouched.
